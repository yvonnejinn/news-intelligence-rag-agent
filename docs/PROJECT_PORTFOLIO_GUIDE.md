# 三、新闻项目全流程

## 1. 定义问题

将新闻项目拆成两个独立任务：

- 情感分类：输入一条新闻文本，输出 negative、neutral 或 positive；
- 检索问答：根据用户问题返回相关新闻片段，再由 Gemini 基于片段回答并标注来源。

拆分原因：分类模型负责稳定标签，RAG 负责事实检索和自然语言回答，二者评测标准不同。

## 2. 数据获取

训练数据采用 Financial PhraseBank `sentences_allagree`，因为它具有专家人工标注，能快速建立可信基线。

最新新闻通过 RSS 获取，保存：

- `document_id`；
- `title`；
- `text`；
- `source`；
- `published`。

不直接把 Gemini 自动标签作为测试集真值，避免用同类模型既生成答案又定义正确答案。

## 3. 数据预处理

步骤：

1. 删除 HTML、脚本和多余空白；
2. 将规范化文本转成 SHA-256 内容哈希；
3. 按哈希删除重复文章；
4. 按固定词数分块，并设置 overlap；
5. 为每块生成稳定的 `document_id:chunk_number`。

稳定 ID 同时用于检索评测和引用约束。

## 4. 情感分类

训练流程：

1. 将标签映射为 negative、neutral、positive；
2. 使用分层 80/20 划分；
3. 通过 FinBERT tokenizer 截断和补齐到固定长度；
4. 使用 Hugging Face Trainer 微调；
5. 按 Macro-F1 选择最佳 checkpoint；
6. 保存模型和 `metrics.json`。

Macro-F1 是主指标，因为三类新闻数量可能不平衡，Accuracy 容易被多数类主导。

## 5. 向量检索

步骤：

1. 用 Sentence Transformer 编码每个新闻块；
2. 对向量进行 L2 归一化；
3. 使用 FAISS 内积索引实现余弦相似度；
4. 对问题编码并返回 top-k 新闻块；
5. 保留文本、来源、标题和相似度。

测试环境没有 FAISS 时使用 NumPy 内积作为功能回退，但正式性能测试应使用 FAISS。

## 6. Gemini RAG

Prompt 包含：

- 只能使用给定 CONTEXT；
- 每个事实必须引用 `[chunk_id]`；
- 上下文不足时明确拒答；
- 不允许创建不存在的引用。

API 失败使用指数退避重试。最终仍失败则抛出错误，而不是返回看似正常的空结果。

## 7. 评测

分类：

- Accuracy；
- Macro-F1；
- 后续补充混淆矩阵和各类别 Recall。

检索：

- Recall@1；
- Recall@3；
- Recall@5。

回答：

- 回答相关性；
- 事实一致性；
- 引用准确率；
- 无答案问题的拒答率；
- 响应延迟；
- 单次调用成本。

## 8. 展示

Streamlit 页面显示：

- 用户问题；
- 最终回答；
- 被检索的证据块；
- 每个证据的来源和相似度；
- 总响应时间。

另一页面用于逐条人工复核 RSS 情感标签。

# 四、新闻项目面试回答

## 30 秒版本

“这个项目把新闻情感分类和检索问答拆成两个模块。分类部分用 Financial PhraseBank 作为专家标注基线，代码支持微调 FinBERT 或 RoBERTa；检索部分先清洗去重和分块，再用 Sentence Transformer 与 FAISS 返回相关证据，最后要求 Gemini 只能依据证据回答并引用 chunk ID。我同时实现了 Macro-F1、Recall@K、引用准确率和延迟评测。目前代码闭环已经完成，但正式模型指标还在等待固定数据集运行，因此简历里没有虚报分数。”

## 为什么不用 Gemini 直接完成所有任务？

“直接调用 Gemini 开发快，但输出一致性、成本和可评测性较弱。稳定的情感标签适合用小模型批量推理，复杂问答再调用大模型。这样可以分别优化准确率、检索效果、延迟和成本。”

## 为什么选择 FinBERT？

“FinBERT 已在金融语料上预训练，对 earnings、guidance、downgrade 等金融表达更敏感。它是领域基线，不代表一定最好，所以代码也允许替换 RoBERTa，并以同一数据划分和 Macro-F1 比较。”

## 为什么不用 Gemini 自动标签直接做测试集？

“这会造成评测闭环偏差。模型生成的标签可能带有同类模型偏好，用它评价 Gemini 或相似模型会高估效果。自动标签可以用于候选筛选，但最终测试集需要人工复核。”

## 如何处理重复新闻？

“当前使用清洗后正文的哈希做精确去重。它能消除完全重复内容，但不能识别轻微改写；下一步会增加 embedding 相似度或 MinHash 做近重复识别。”

## 为什么需要 overlap？

“没有 overlap 时，关键事实可能恰好被切在两个块之间。适量重叠能保留上下文，但会增加索引大小并产生重复证据，所以需要用 Recall@K 和延迟一起调参。”

## FAISS 为什么使用内积？

“文档向量和查询向量都先做 L2 归一化。归一化后内积等价于余弦相似度，因此可以使用 `IndexFlatIP`。”

## Recall@K 是什么？

“对每个评测问题先人工标出相关 chunk ID。如果 top-k 结果覆盖了相关 chunk，就计入召回。它只衡量检索阶段，不会被 Gemini 的生成质量干扰。”

## 如何降低幻觉？

“我没有笼统声称消除幻觉，而是使用来源 ID、仅基于上下文、上下文不足拒答和引用格式检查。进一步需要人工事实一致性评测，才能量化改善。”

## 项目当前最大的不足是什么？

“目前缺少固定的最新新闻人工测试集和正式运行指标。下一步优先补齐 150 条人工复核数据，再比较零样本、微调模型和不同检索参数。”

# 五、贷款项目全流程

## 1. 定义任务

输入申请人在审批时点可获得的特征，输出 `loan_status=1` 的概率。

这是历史审批结果预测，不是贷款违约预测。`cb_person_default_on_file` 是申请人过往是否有违约记录的输入特征，不是当前贷款的结果。

## 2. 数据审计

检查：

- 训练和测试列是否一致；
- 目标列和正类比例；
- 空值和数据类型；
- ID 唯一性；
- 整行重复；
- 同特征不同标签；
- 目标复制字段；
- 审批后字段。

实际结果：无缺失值、无整行重复、无冲突重复特征、无目标复制；删除唯一 ID `id`。

## 3. 特征工程

只创建审批时可获得的变量：

- 贷款收入比；
- 年龄和利率交互；
- 年化利息代理变量。

所有按数据学习的处理，包括填补、编码和缩放，均在交叉验证 fold 内拟合。

## 4. 类别不平衡

正类比例为 14.24%。当前基线：

- Logistic Regression 使用 `class_weight=balanced`；
- Random Forest 使用 `class_weight=balanced`；
- 使用分层交叉验证；
- 同时报告 PR-AUC、Recall 和 F1。

SMOTE 尚未执行。正确做法是仅在每个训练 fold 内进行，不能先对全体数据 SMOTE 再切分。

## 5. 模型比较

当前实际比较：

- Logistic Regression：可解释的线性基线；
- Random Forest：捕捉非线性与特征交互。

代码支持安装后加入 XGBoost 和 LightGBM，但当前不能声称它们的结果。

## 6. 交叉验证

使用 3 折 StratifiedKFold：

1. 每折只用训练 fold 拟合预处理和模型；
2. 对验证 fold 生成概率；
3. 合并所有 fold 得到完整 OOF 概率；
4. 基于 OOF 概率计算指标；
5. 按 PR-AUC 选择基线模型。

OOF 指标比单次 train/test split 更稳定，也能为所有训练样本提供未见过该样本的预测概率。

## 7. 概率校准

对最佳 Random Forest 进行 Sigmoid 校准。

结果：

- ROC-AUC：0.9348 → 0.9351；
- Brier：0.0478 → 0.0441。

ROC-AUC 变化很小是正常现象，因为校准主要改善概率含义，不一定改变样本排序。

## 8. 阈值分析

Kaggle 提交概率，不要求固定分类阈值。阈值分析用于模拟业务决策。

当前使用等 false-positive/false-negative 成本，最优阈值为 0.59。真实业务中必须由业务部门定义两类错误成本，不能直接把 0.59 当成银行政策。

## 9. 模型解释

代码包含 SHAP 入口，设计目标是：

- 全局特征影响；
- 单个申请的局部解释；
- 检查模型是否过度依赖异常变量。

当前环境未安装 SHAP，因此没有生成图，也不能声称具体特征排名。

## 10. 实验追踪和交付

脚本会生成：

- 泄漏报告；
- 指标 JSON；
- 模型文件；
- Kaggle submission。

MLflow 可用时记录参数、指标和产物；当前实际运行使用本地 JSON 作为审计证据。

# 六、贷款项目面试回答

## 30 秒版本

“我使用 Kaggle S4E10 的 58,645 条贷款申请数据预测审批结果。首先检查 ID、重复数据、目标复制和审批后字段，并把所有预处理放入交叉验证 Pipeline。由于正类只有 14.24%，我使用分层 OOF 验证并重点比较 PR-AUC。Random Forest 达到 ROC-AUC 0.9348、PR-AUC 0.8398，校准后 Brier Score 从 0.0478 降到 0.0441。我还完成了阈值分析、模型持久化和 39,098 行提交文件校验。这个数据预测审批，不是违约，所以我不会把它描述成信用违约模型。”

## 为什么这个项目不能叫违约预测？

“目标 `loan_status` 表示历史上是否获批，没有未来还款结果。虽然存在历史违约特征，但那只是输入。没有 default outcome 就无法训练概率违约模型。”

## 你如何检查数据泄漏？

“我检查目标复制、审批后字段名、唯一 ID、重复数据和同特征不同标签。更重要的是，把填补、编码和缩放都放进 fold 内 Pipeline，防止验证数据影响训练处理参数。”

## `cb_person_default_on_file` 为什么不是泄漏？

“它描述申请人申请之前的历史违约记录，在审批时已经可用。是否泄漏取决于时间点，不是列名里出现 default 就一定泄漏。”

## 为什么用分层交叉验证？

“正类只有 14.24%。普通随机切分可能导致各折正类比例波动，分层能保持标签比例，使 PR-AUC、Recall 和 F1 更稳定。”

## 为什么 Kaggle 用 ROC-AUC，你还要看 PR-AUC？

“ROC-AUC 与公榜一致，衡量排序能力；但在正类较少时，大量真负例会让 ROC-AUC 看起来较好。PR-AUC更集中反映正类识别质量，所以我用两者共同判断。”

## 为什么 Random Forest 比 Logistic Regression 好？

“结果说明数据中存在非线性和交互。Logistic Regression 的 ROC-AUC 为 0.9053，Random Forest 为 0.9348。但线性模型仍有价值，它提供稳定基线并帮助检查复杂模型是否真正增加价值。”

## 为什么要概率校准？

“AUC只关心排序。如果0.8并不对应约80%的实际正类比例，就不适合阈值或资源配置。校准后 Brier 从0.0478降到0.0441，说明概率误差下降。”

## 校准后 PR-AUC略微下降怎么办？

“校准目标是概率可靠性，不是提高排序。PR-AUC从0.8398到0.8392，变化很小；同时Brier明显下降，所以这是预期的权衡，不应该挑一个指标单独宣布全面提升。”

## 阈值0.59怎么得到？

“在 OOF 校准概率上枚举阈值，计算 false positive 和 false negative 的加权成本。当前两种错误成本都设为1，最低成本点是0.59。真实应用需要替换成业务成本。”

## 为什么暂时没用 SMOTE？

“类别权重已经提供可靠基线。SMOTE不保证提升，而且类别和连续变量混合时要谨慎；如果使用，必须放在训练 fold 内，并用相同 OOF 协议比较 PR-AUC 和校准结果。”

## 0.9582 公榜分数在哪里？

“当前仓库没有可以验证该数字的 Kaggle记录，所以我没有把它写入 README。现在可复现的是 OOF ROC-AUC 0.9351；新 submission 已生成，只有 Kaggle 返回结果后才能增加公榜分数。”

## SHAP 和 MLflow 做了吗？

# 七、常见压力追问应对原则

## 不知道时怎么回答

使用以下结构：

1. 明确当前事实；
2. 说明缺少什么证据；
3. 给出验证方法；
4. 不编造结果。

示例：

“我目前还没有运行 LightGBM，因此不能判断它是否优于 Random Forest。代码会让它使用同一组 folds，比较 OOF ROC-AUC、PR-AUC 和 Brier，只有结果稳定后我才会更新简历。”

## 面试官质疑项目只是调包

回答重点：

- 你定义了任务边界和标签含义；
- 你处理了数据时点和泄漏；
- 你选择了适合不平衡问题的指标；
- 你区分排序、概率和阈值；
- 你建立了可复现产物和失败保护；
- 你知道当前证据的限制。

## 面试官问最大收获

新闻项目：

“最大的收获是把分类、检索、生成分开评测。RAG回答不好时，必须先判断是检索没找到证据，还是模型没有忠实使用证据。”

贷款项目：

“最大的收获是AUC高不等于概率可靠，也不等于可以直接制定业务决策。排序、校准和阈值必须分开验证。”

# 八、绝对不要声称的内容

新闻项目暂时不要声称：

- FinBERT达到某个F1；
- 微调优于Gemini多少；
- RAG降低幻觉多少；

- Kaggle公榜AUC 0.9582；
- XGBoost或LightGBM优于RF；
- Optuna或SMOTE带来提升；
- 已得出SHAP特征结论；
- 已使用MLflow完成实验管理；
